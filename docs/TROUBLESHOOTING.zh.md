# 排查问题

所有提供方初始都是**关闭**的，所以第一件该试的事永远是同一件：在 **设置 → 模型请求加速** 里把开关关掉。改动是实时的（无需重启），效果就是回到安装本插件之前的行为。

## 模型请求失败或回答异常

在设置页把该提供方的开关关掉再试一次。

- **关掉就好了。** 原因在压缩或预传输，见下文。
- **关掉仍然失败。** 那就不是本插件造成的——除非日志里出现了针对该请求的行。去 Host 输出里找 `model-request-accelerator:` 开头的行。

如果插件自己的改写过程抛错，它会退回为不压缩地发送请求，所以本插件的 bug 不会弄坏模型请求。即便如此仍想确认，卸载是即时且可逆的——见 README。

## 压缩

**症状：开启压缩后请求失败。**

你的网关可能无法解码该编码。有两件事会自动发生：对 brotli body 回 `411`/`415`/`501` 的请求会用 gzip 重试；反复拒绝某编码的 endpoint 会被关闭压缩。所以最坏情况是每个 endpoint **一次性**多一个请求。

想在依赖它之前确认，或想知道究竟发生了什么：

```bash
node scripts/probe-encodings.mjs https://your-gateway.example/v1
```

它发的是单 token 请求而不是真实对话。如果你根本不想让它尝试 brotli，把**算法**设为 `gzip`——gzip 几乎无处不在，拒绝它的网关很罕见。

**症状：日志里有请求，但没有任何压缩记录。**

低于 `minBytes`（默认 `1024`）会跳过压缩；压缩后不会更小时也会跳过。小的 JSON body 往往不值得压缩，原样发送是正确答案而不是失败。

**去哪里看：** Host 会为每个被压缩的请求打一行日志。

```
model-request-accelerator: sg request compressed 3813841 -> 1461179 bytes
```

请求无法归属到提供方时，会出现 `endpoint-matched` 而不是提供方名字。

## 预传输

**症状：耗时行上没有 预热 标记。**

两种可能：

1. **该请求无法归属到提供方。** 日志里是 `endpoint-matched` 而不是提供方名字。当请求在流式模型调用之外到达 `fetch` 时会这样。
2. **endpoint 拒绝了 chunked body**，于是对它关闭了预传输。设置卡片会说明——见 [读懂 endpoint 报告](#读懂-endpoint-报告)。

被持有的请求必须携带 **chunked** body，因为增量到来之前它的长度无法得知。不接受这一点的 endpoint 无法支持该特性，插件会停止尝试，而不是让每个请求都退化。

**症状：预传输本来有效，后来不生效了。**

看看确实用过它的那一行的 预热 提示。如果池一直被重建，很可能是该 endpoint 拒绝了重排后的 body——插件随即对该 endpoint 退回适配器自己的字段顺序并记住它。这是正确性兜底而不是故障：请求照常工作，只是在那里不走预传输。

**症状：能看到被持有的连接一直开着。**

这正是该特性的形态。一个对话会持有 `prewarmPoolSize` 个请求（默认 `2`），它们在**空闲** `prewarmHoldMs`（默认 `120000`，两分钟）后过期——每次推进都会重置计时器。对话闲置时不会有任何重连，因为成员只由被捕获的请求打开。把 `prewarmPoolSize` 降到 `1` 就是最小可用的池。

## HTTP/2

**症状：耗时行没有 `h2` 标记。**

最可能是你的网关不提供 HTTP/2——那样请求会继续走 HTTP/1.1，**并没有出问题**。h2 通过 ALPN 达成，不提供它的 endpoint 就继续用 HTTP/1.1。

该标记**只在响应确实经 h2 返回时**才出现。「请求了 h2」和「用了 h2」不是一回事，插件刻意不把它们当成一回事。

**症状：设置卡片说某个 endpoint 被放弃了。**

插件会尝试 h2；若传输层彻底失败，它会在本插件的生命周期内放弃该 **origin**——代价是**一次性**多一个往返，而不是每请求一个。请求继续走 HTTP/1.1。重启 `dsh web` 会清掉这个决定并允许重试。

**症状：`http://` 的 endpoint 没用 h2。**

明文 h2c 默认关闭。`allowInsecureH2c: true` 可以打开，但那是**没有证书**的连接——只在你信任那条链路时才开。

## 耗时视图

**视图不见了。** 它只在 **显示请求耗时视图** 开启时存在。在设置页打开它；标签会立即出现，无需刷新页面。

**面板是空的。** 它列出当前会话的请求。新会话就先发一次模型调用。如果刚清空过账本，那历史是**按设计**没了——清空不可撤销，且会同时丢弃已存文档和运行进程持有的部分。

**某一行的响应体是 `–`。** 表示完全没有任何 chunk 被归属到该请求。这是值得看见的接线故障，而不是空回复——请反馈。

**某一行的预传输标记处是 `不适用`。** 该请求体没有可以追加对话的顶层数组，所以预传输对它不适用。见 [INTERNALS.md](./INTERNALS.md#request-body-shapes)（英文）。

## 设置页面

**页面不见了，或开关全是灰的且都关着。**

先刷新浏览器标签页——卡片属于页面的模块图，安装时已开着的标签页不会有它。仍然没有的话，说明插件没载入：去 Host 输出里找提到 `model-request-accelerator` 的错误。

**保存时报 `Configuration for "model-request-accelerator" is overridden by a home patch or command-line overlay`。**

这说明插件的设置不在本版本读取的位置——典型的「1.7.x 升级上来但没有跑迁移」。见 **[UPGRADING.zh.md](./UPGRADING.zh.md)**。

**保存时报 `Config field "..." is not volatile`。**

你跑的是 2.0.0 或 2.0.1 的 Host half 配着更新的页面。更新后重启 `dsh web`，或升到 2.0.2 以上。

## 读懂 endpoint 报告

设置卡片会按 endpoint 报告真实流量已经确立了哪些事实：

- 某个压缩 body 是否曾被**拒绝**，以及是否因此从 brotli 换成了 gzip；
- 是否因为该 endpoint 不接受 chunked body 而**关闭了预传输**；
- 连续失败了多少次压缩尝试。

它是观察记录，**不是探测**——不会为了产生它而发送任何东西——并且在有值得报告的事之前保持沉默。表现正常的 endpoint 干脆什么都不说，这才是正常且健康的状态。想在产生流量之前问清楚，用 `scripts/probe-encodings.mjs`。

## 本插件做不到的事

把边界说清楚能省下以后的时间：

- **无法压缩已签名的 body。** 携带 `x-amz-content-sha256`（AWS 风格签名）的请求会被放过：签名覆盖 body 的字节，压缩会破坏签名——而由此产生的鉴权失败**不是**形状拒绝，所以「编码被拒后回退」那条路永远不会触发。Bedrock 类传输因此不在范围内。
- **看不到不走 `fetch` 的传输。** WebSocket，或自带 HTTP 栈的 SDK，永远不会经过它。
- **不提供 HTTP/3。** 这套技术栈上够不着——见 [INTERNALS.md](./INTERNALS.md#http3)（英文）。
- **不能让模型更快。** 它把字节移出关键路径并缩小它们，不改变模型拿它们做什么；在链路很快、上下文很小时，它甚至可能比不做更慢。
- **不能压缩响应。** 响应本来就由运行时压缩；本插件的压缩只针对请求。
